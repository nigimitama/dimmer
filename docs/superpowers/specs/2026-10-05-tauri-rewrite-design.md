# Dimmer の Tauri + React/TypeScript への書き直し：設計

- 日付：2026-10-05
- ステータス：レビュー待ち
- 対象バージョン：1.0.0

## 1. 目的と背景

Dimmer は、DDC/CI 対応の外部モニターの輝度を一括・個別に制御し、時刻ごとのスケジュールで自動的に調整する Windows 向けの常駐アプリである。現在は Python（tkinter + sv-ttk、`monitorcontrol`、`schedule`、`pystray`）で実装され、PyInstaller の単一 exe として配布している。

これを Tauri v2 + React + TypeScript で書き直す。理由は次の4つ。

1. **見た目と UI の自由度**：tkinter では UI の表現に限界がある
2. **exe のサイズと起動の速さ**：PyInstaller の onefile 形式は大きく、起動が遅い
3. **Microsoft Store での配布**：将来的に Store で配布したい（今回のスコープ外。9章を参照）
4. **スリープ復帰後にスケジュールが動かなくなるバグ**：現状は復帰後にスケジュールが効かず、結局毎回手動で操作している

### 成功の基準

- スリープ復帰、アプリ起動、モニターの抜き差しのいずれの後でも、その時刻にスケジュールで設定された輝度に自動で戻る
- 現行の機能（一括・個別の輝度調整、スケジュール、トレイ常駐、ダーク/ライト追従）がすべて使える
- 追加機能として、ログイン時の自動起動とモニター名の表示がある
- GitHub Releases で NSIS インストーラーを配布できる

### 前提と制約

- 対象は Windows 10/11 のみ
- 既存の `dimmer.json` は引き継がない。設定ファイルの形式は新しく定義する
- パッケージマネージャーは pnpm

## 2. 機能範囲

| 機能 | 現行 | 新版 |
|---|---|---|
| 全モニター一括の輝度調整（10刻みのスライダー） | あり | あり |
| モニター個別の輝度調整 | あり（別タブ） | あり（同じ画面に常に表示） |
| 毎日のスケジュール（時刻 → 輝度） | あり | あり（ロジックを作り直す） |
| スリープ・起動時に直近のスケジュール値を適用 | なし（バグ） | **あり** |
| トレイ常駐（×で隠す、表示/非表示、終了） | あり | あり |
| OS のダーク/ライトに追従 | あり | あり |
| ログイン時の自動起動（設定で on/off） | なし | **あり** |
| モニターの製品名を表示 | なし（「Monitor 1」） | **あり** |
| 二重起動の防止 | なし | **あり** |

入れないもの：トレイメニューからの輝度変更、スケジュールの有効/無効の切り替え、グラフ上でのドラッグ編集、モニター個別のスケジュール。

## 3. 全体構成

Rust 側にすべてのロジックと状態を持たせ、React は表示と操作の受け付けだけを行う。非表示の WebView ではタイマーが間引かれたり止まったりするため、スケジュールの判定は必ず Rust 側で動かす。

```
dimmer/
├─ src/                  React + TypeScript（Vite）
│  ├─ api.ts             command / event の型付きラッパー
│  ├─ components/        画面コンポーネント
│  └─ lib/               純粋関数（スケジュールの検証、グラフの座標計算）
└─ src-tauri/
   └─ src/
      ├─ main.rs / lib.rs
      ├─ monitor.rs
      ├─ schedule.rs
      ├─ scheduler.rs
      ├─ settings.rs
      ├─ commands.rs
      └─ tray.rs
```

### 3.1 Rust モジュール

| モジュール | 役割 | 依存先 |
|---|---|---|
| `monitor.rs` | DDC/CI でモニターを列挙し、ID と名前付きで輝度を get/set する。`MonitorBackend` トレイトとして定義し、テストではモックに差し替える | `ddc-hi` |
| `schedule.rs` | 純粋関数のみ。スケジュールと現在時刻から現在のスロットを返す。I/O を持たない | なし |
| `scheduler.rs` | 30秒ごとの tick ループ。スロットの変化、スリープ復帰、モニター構成の変化を検知して輝度を適用する。時計は差し替えられるようにする | monitor, schedule, settings |
| `settings.rs` | 設定ファイルの読み書きと検証 | serde, serde_json |
| `commands.rs` | React から呼ぶ Tauri command | 上記すべて |
| `tray.rs` | トレイアイコンとメニュー（表示/非表示、終了）。ウィンドウの × ボタンで隠す処理 | Tauri 標準の tray API |

使用するプラグイン：

- `tauri-plugin-autostart`：ログイン時の自動起動
- `tauri-plugin-single-instance`：二重起動の防止。2つ目を起動したときは既存のウィンドウを表示して前面に出す
- `tauri-plugin-log`：ログをアプリのログフォルダにファイル出力する

DDC へのアクセスは `Mutex` で直列化し、スケジューラーと手動操作が同時に DDC と通信しないようにする。

### 3.2 モニターの識別と名前

- 個別操作はインデックスではなく、`ddc-hi` が返すモニター ID で指定する。抜き差しで順番が変わっても操作対象がずれないようにするため
- 名前は次の順で取得する：(1) `ddc-hi` の EDID 情報の model name、(2) DDC capabilities 文字列の `model(...)`、(3) WMI の `WmiMonitorID`、(4) どれも取れなければ `Monitor N`
- (1) で Windows 上の名前がどこまで取れるかは実機で確認が必要。最初の実装タスクで確かめ、取れない場合だけ (2) 以降を実装する

## 4. データモデル

### 4.1 設定ファイル

保存先：Tauri の `app_config_dir()` の下の `settings.json`（`%APPDATA%\<identifier>\settings.json`）

```json
{
  "version": 1,
  "autostart": true,
  "schedule": [
    { "time": "06:00", "brightness": 70 },
    { "time": "07:00", "brightness": 80 }
  ]
}
```

- `time`：`"HH:MM"`（24時間表記、ゼロ埋め）
- `brightness`：0〜100 の整数
- 保存時に `time` の昇順でソートする
- 次のいずれかに当てはまる場合は保存を拒否し、エラーを返す：同じ `time` が重複している、`time` の形式が不正、`brightness` が範囲外
- ファイルがない場合（初回起動）はデフォルト値を書き込む。`autostart` のデフォルトは `true` とし、初回起動時に自動起動を登録する
- ファイルが壊れている（パースできない、または検証に失敗する）場合は `settings.json.bak` に退避してからデフォルト値で起動し、ログに記録する

デフォルトのスケジュール（現行と同じ）：

| 時刻 | 06:00 | 07:00 | 08:00 | 09:00 | 17:00 | 18:00 | 19:00 | 20:00 | 21:00 | 22:00 | 23:00 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 輝度 | 70 | 80 | 90 | 100 | 90 | 80 | 60 | 40 | 30 | 10 | 0 |

### 4.2 スロット

スケジュールを「時刻ごとの目標輝度」として扱う。

- **現在のスロット**：時刻が現在時刻以前のエントリのうち、最も遅いもの。当日のエントリがまだ1つもなければ、前日の最後のエントリを使う（例：2:00 なら前日 23:00 のエントリ）
- 境界の時刻ちょうど（例：18:00:00）は、その時刻のエントリのスロットに含める
- **スロット ID**：そのエントリが発生した日時（例：`2026-10-05T18:00`）。同じエントリでも日付が違えば別のスロットとして扱う
- スケジュールが空ならスロットはなく、スケジューラーは何もしない
- 時刻はローカルタイムで扱う

`schedule.rs` が公開する関数：

```rust
pub struct Slot { pub id: NaiveDateTime, pub brightness: u8 }
pub fn current_slot(entries: &[ScheduleEntry], now: NaiveDateTime) -> Option<Slot>;
pub fn next_slot(entries: &[ScheduleEntry], now: NaiveDateTime) -> Option<Slot>;
```

## 5. スケジューラー

### 5.1 状態

```rust
struct SchedulerState {
    last_applied: Option<NaiveDateTime>, // 適用済みのスロット ID
    last_tick: Option<NaiveDateTime>,    // 前回 tick の壁時計時刻
    last_monitor_ids: Vec<String>,       // 前回の列挙結果（ソート済み）
}
```

### 5.2 tick の処理（30秒ごと）

1. 現在の壁時計時刻 `now` を取得する
2. `last_tick` から 90秒以上経っていたら **復帰とみなす**（スリープ復帰のほか、OS の時刻変更でも成立する。どちらの場合も再適用して問題ない）
3. モニターを列挙し、ID の集合が `last_monitor_ids` と違えば **モニター構成の変化とみなす**。列挙は DDC 通信を伴わない
4. `current_slot(entries, now)` を計算する
5. スロットがあり、かつ次のいずれかに当てはまれば、全モニターにそのスロットの輝度を適用する：
   - スロット ID が `last_applied` と違う
   - 復帰とみなした
   - モニター構成が変化した
   - 起動後最初の tick である
6. 適用に失敗したモニターがあれば、5秒後と15秒後にリトライする（最大3回）。リトライは tick ループを止めずに別タスクで行う
7. すべてのモニターで成功したら `last_applied` を更新し、`monitors-updated` イベントを送る。リトライしても失敗した場合は `last_applied` を更新せず、ログに残す。次の tick でまた試す
8. `last_tick = now`、`last_monitor_ids` を更新する

これにより、現行の「set を2回呼ぶ」回避策はリトライで置き換える。

### 5.3 手動操作とスケジュール編集との関係

- 手動で輝度を変えても、スケジューラーの状態は変えない。次のスロットに切り替わるまでは手動の値が維持される
- スケジュールを保存したときは、保存後のスケジュールで計算した現在のスロット ID を `last_applied` に設定する。編集した瞬間に輝度が変わらないようにし、次のスロットから新しいスケジュールを効かせるため
- 「デフォルトに戻す」も保存と同じ扱いにする

## 6. Rust と React のインターフェース

### 6.1 command

| 名前 | 引数 | 戻り値 | 内容 |
|---|---|---|---|
| `get_monitors` | なし | `Monitor[]` | 列挙して現在の輝度を読む |
| `rescan_monitors` | なし | `Monitor[]` | 再列挙する（モニターが見つからないときの再検出ボタン用） |
| `set_brightness_all` | `value: u8` | `ApplyResult` | 全モニターに適用する |
| `set_brightness` | `id: string, value: u8` | `ApplyResult` | 1台に適用する |
| `get_settings` | なし | `Settings` | |
| `save_schedule` | `entries: ScheduleEntry[]` | `Settings` / 検証エラー | 検証・ソートして保存し、5.3 の処理を行う |
| `reset_schedule` | なし | `Settings` | デフォルトのスケジュールで保存する |
| `set_autostart` | `enabled: bool` | `Settings` | プラグイン経由で登録/解除し、設定に保存する |

```ts
type Monitor = { id: string; name: string; brightness: number | null }; // 読めなければ null
type ApplyResult = { failed: { id: string; name: string; error: string }[] };
```

### 6.2 event

| 名前 | ペイロード | 送るタイミング |
|---|---|---|
| `monitors-updated` | `Monitor[]` | スケジュールの適用後、モニター構成の変化後 |

React は起動時に `get_monitors` と `get_settings` を呼び、以降は `monitors-updated` を購読して表示を更新する。

## 7. UI

### 7.1 画面構成

タブのない1画面にする。ウィンドウサイズは 520×640 前後。

- **上段（輝度）**
  - 「すべて」のスライダー：値は各モニターの輝度の平均（四捨五入）。動かすと全モニターに適用する
  - モニターごとのスライダー：モニター名と値を表示する
  - スライダーは 0〜100、**10刻み**。ドラッグ中は表示だけを更新し、100ms のデバウンス後に command を送る
  - モニターが1台も見つからない場合は、スライダーの代わりに「DDC/CI 対応のモニターが見つかりません」と再検出ボタンを表示する
- **下段（スケジュール）**
  - 見出しに次の変更を表示する（例：「次 19:00 → 60%」）
  - 24時間の階段グラフ（表示専用）。横軸 0〜24時、縦軸 0〜100%。現在時刻に縦線を引く。0時から最初のエントリまでは前日の最後のエントリの値で描く
  - 編集用のリスト：各行に時刻入力、輝度の数値入力（0〜100 の整数）、削除ボタン。現在のスロットの行を強調する
  - リストの末尾に「＋ 追加」と「デフォルトに戻す」。追加される行の初期値は 00:00 / 50
  - 編集のたびに自動保存する。検証エラー（時刻の重複、範囲外の値）は該当する行に赤字で表示し、エラーがある間は保存しない
- **設定ダイアログ**（右上の ⚙ ボタン）：「ログイン時に起動」のトグルとバージョン表示

### 7.2 見た目

- UI ライブラリは Fluent UI React v9
- グラフは SVG で自前で描く（グラフ用のライブラリは入れない）
- OS のダーク/ライト設定に追従する。Fluent のテーマ、ウィンドウのテーマ、トレイアイコン（`icon-dark` / `icon-light`）を切り替える
- アイコン画像は既存の `assets/` のものを流用する

### 7.3 ウィンドウとトレイ

- × ボタンでウィンドウを隠し、アプリは終了しない
- トレイアイコンの左クリックとメニューの「表示/非表示」でウィンドウを切り替える。メニューの「終了」でアプリを終了する
- 自動起動で起動したときは、ウィンドウを表示せずトレイに常駐する（`tauri-plugin-autostart` の起動引数で判定する）。手動で起動したときはウィンドウを表示する

## 8. エラー処理とログ

- DDC の失敗はモニター単位で扱う。1台が失敗しても残りには適用し、失敗した分を `ApplyResult.failed` で返す。React はトーストで表示する
- 輝度を読めなかったモニターは `brightness: null` とし、UI ではスライダーを無効にして「読み取れません」と表示する
- スケジューラーの失敗の扱いは 5.2 のとおり
- 復帰の検知、スロットの適用、リトライ、失敗はすべて `tauri-plugin-log` でファイルに記録する

## 9. スコープ外：Microsoft Store 対応

Store に EXE/MSI インストーラーを提出するには、Microsoft Trusted Root Program に含まれる認証局のコード署名証明書が必要になる。MSIX なら Store 側で署名されるが、Tauri は MSIX を公式には出力せず、自動起動も MSIX 用の `StartupTask` に変える必要がある。どちらにするかは別のサブプロジェクトで決める。

今回の実装では、後から Store に対応しやすくするために次の点を守る。

- 設定の保存先は Tauri 標準のパス（`app_config_dir()`）を使い、実行ファイルの場所やカレントディレクトリに依存しない
- 自動起動の登録/解除は `set_autostart` command の中に閉じ込め、実装を差し替えられるようにする

## 10. テスト

### 10.1 自動テスト

- `schedule.rs`
  - 日付をまたぐ場合（0:00〜最初のエントリまでは前日の最後のエントリになる）
  - 境界の時刻ちょうど
  - エントリが1つだけの場合、空の場合
  - `next_slot` が翌日に回り込む場合
- `scheduler.rs`（`MonitorBackend` のモックと差し替え可能な時計を使う）
  - スロットが変わったときだけ適用される
  - 90秒以上の間隔が空くと、同じスロットでも再適用される
  - モニター構成が変化すると再適用される
  - 起動後最初の tick で適用される
  - 失敗するとリトライし、成功するまで `last_applied` が更新されない
  - 手動で設定した値が、同じスロットの間は上書きされない
  - スケジュールを保存すると、現在のスロットが適用済みになる
- `settings.rs`：読み書きの往復、時刻の重複・形式不正・範囲外での拒否、壊れたファイルの退避とデフォルトでの起動、ソート
- React（Vitest）：スケジュールの検証ロジック、グラフの座標計算（日付をまたぐ部分を含む）

E2E テストは入れない。

### 10.2 実機での確認項目

リリース前に手動で確認する。

- [ ] スケジュール時刻をまたいでスリープし、復帰すると直近の値が適用される
- [ ] 復帰直後に DDC が失敗しても、リトライで適用される
- [ ] モニターを抜き差しすると、一覧が更新され、直近の値が適用される
- [ ] 手動で変えた値が、次のスケジュール時刻まで維持される
- [ ] 自動起動を有効にすると、ログイン後にトレイに常駐し、ウィンドウは開かない
- [ ] 二重起動すると、既存のウィンドウが前面に出る
- [ ] OS のダーク/ライトを切り替えると、UI とトレイアイコンが追従する
- [ ] モニター名が表示される（取得できない場合は「Monitor N」になる）
